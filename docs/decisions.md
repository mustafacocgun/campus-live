# Decisions

Why the stack is what it is. Each entry: the decision, the reason, and what would make us revisit it.
Team decisions are dated; "open" items live in CLAUDE.md §6.

| #   | Decision                                                                                                                                     | Why                                                                                                                                     | Revisit when                                             |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| D1  | One npm-workspace monorepo (`apps/`, `services/`, `packages/`)                                                                               | Web, mobile and API share one set of types, so a contract change fails at compile time                                                  | Build times hurt; then add Turborepo on top              |
| D2  | `packages/contracts` (zod) is the single contract; JSON Schema is generated for Python                                                       | One source of truth across TypeScript and Python                                                                                        | Never; extend it instead                                 |
| D3  | The vision service pushes readings to the API (`POST /internal/readings`)                                                                    | Vision is the producer; cameras can run on several machines and push to one API                                                         | Many cameras: put a queue (Redis) between them           |
| D4  | Live state in API memory; Socket.IO to clients; REST for the first load                                                                      | Fewest moving parts for a live demo; Socket.IO reconnects on flaky Wi-Fi                                                                | History and alerts land: add Postgres                    |
| D5  | Apps show numbers and colors only, never camera images (team, 2026-10-27); narrowed by D33                                                   | Frames never leave vision (KVKK); no faces republished                                                                                  | Never without a CLAUDE.md §0.2 change                    |
| D6  | Footage: licensed or our own first; YouTube maybe later (team, 2026-10-27)                                                                   | Licenses and consent are defensible on stage                                                                                            | The team decides otherwise, recorded here                |
| D7  | Express 5 + TypeScript for the API (team, 2026-10-27)                                                                                        | The team already used it in campus-life                                                                                                 | —                                                        |
| D8  | Expo SDK 58 for mobile (team, 2026-10-27)                                                                                                    | Same TypeScript and types as web; Expo Go on phones during the hackathon                                                                | Native modules Expo Go cannot load                       |
| D9  | One React (19.3.0) pinned by root `overrides`                                                                                                | Expo pins React exactly; two copies break React Native hooks                                                                            | Expo SDK upgrade: move the pin with it                   |
| D10 | The assistant lives in the API: an OpenAI-compatible adapter, a grounded prompt, a rule-based fallback                                       | The API holds the live state; any provider plugs in; the demo works without a key                                                       | The team picks a provider with a different API           |
| D11 | No user accounts in v1; superseded by D26 (2026-10-28)                                                                                       | Following a parking lot can use the phone's push token                                                                                  | Features need identity                                   |
| D12 | Crowd → parking → traffic (team, 2026-10-27)                                                                                                 | Crowd reuses the most; parking has the clearest user value; traffic is cut first                                                        | —                                                        |
| D13 | MapLibre GL draws the web map (team, 2026-10-27)                                                                                             | A GPU heatmap layer gives the smooth "temperature cloud" the team asked for; Leaflet's heat plugin is unmaintained since 2022           | —                                                        |
| D14 | Live YOLO is the only data source (team, 2026-10-27); supersedes the simulated mode                                                          | Random data made the map look fake; every teammate runs vision on a GPU PC. Tests use the `test-boxes` detector on synthetic clips      | Nobody can run YOLO for the demo                         |
| D15 | MapLibre React Native on mobile, with an Expo development build (team, 2026-10-27)                                                           | The same heat cloud as the web on both phones; Expo Go cannot load it                                                                   | The build cannot be made in time: fall back to the web   |
| D16 | Vision sends aggregated 3 m density cells, never per-person positions                                                                        | Privacy by design (only aggregates leave the machine that saw the video), and it is exactly what a heatmap needs                        | —                                                        |
| D17 | Camera spots come from OpenStreetMap features, as placeholders                                                                               | Grounded in the real campus (library, dining hall, faculties) instead of invented; the team moves them                                  | The team picks real spots                                |
| D18 | WILDTRACK is the footage core, with its real calibration (team, 2026-10-27)                                                                  | 7 overlapping, calibrated HD cameras over one plaza: crowds move from view to view on the map with real geometry                        | The license or the files turn out unusable               |
| D19 | Camera positions never leave the server: the public API, socket events and the apps carry places and the merged heat only (team, 2026-10-28) | Someone could use a map of cameras to avoid or target them. Hiding pins in the page is not enough: `/api/cameras` served every position | —                                                        |
| D20 | Users see places (areas, buildings, parking lots, roads from OpenStreetMap); cameras feed places (team, 2026-10-28)                          | People ask about places, not cameras; a place's count can merge overlapping views, so one crowd is not counted twice (#23)              | —                                                        |
| D21 | Indoor cameras light up their whole building and send counts only (team, 2026-10-28)                                                         | No position inside a building leaves vision, and several floors simply add up                                                           | —                                                        |
| D22 | Parking: each slot is outlined once per camera; a slot is taken when a vehicle covers it (team, 2026-10-28)                                  | Exact free/total per lot; cars driving through the lot do not count as parked                                                           | Too many slots to outline: count cars against capacity   |
| D23 | Traffic: vehicles in each road camera's zone give a level per road (2026-10-28)                                                              | Readable on a map (a red road) with the detector we have                                                                                | The team wants vehicles per minute: count line crossings |
| D24 | OpenFreeMap Liberty with 3D buildings, in light and dark mode (team, 2026-10-28)                                                             | Colorful and campus-like; the team found the dark map plain. 3D only from zoom 14, with a 2D/3D toggle                                  | A device draws 3D too slowly                             |
| D25 | WILDTRACK cut into 5-minute clips, looped, assigned at random per camera with a fixed seed (team, 2026-10-28)                                | Every camera shows a different crowd and the setup can be reproduced; the plaza's 7 views share one clip index, so they stay in sync    | —                                                        |
| D26 | The assistant's LLM: Google AI Studio's free tier, `gemini-3.5-flash-lite`, via its OpenAI-compatible endpoint (team, 2026-10-28)            | Free; eval: ~1 s, Turkish, numbers exact. Free Gemma 4 and local models failed. Google may read questions: no personal data             | Free-tier limits or outages; a budget; EEA/UK users      |
| D27 | The assistant's "nearest"/"where" answers use the user's position (device or map pick) on the server only (team, 2026-10-28)                 | The AI sees just the top 3 places, distances from the user rounded to 50 m; the position is never stored, logged or sent on             | Users want routes; a paid LLM with no human review       |
| D27 | Accounts: school e-mail (`ALLOWED_EMAIL_DOMAINS`) + password, one mailed 6-digit code at sign-up (team, 2026-10-28)                          | Place alerts need someone to notify; the code proves the address is theirs, so nobody can sign another person up for mail               | Single sign-on with the university                       |
| D28 | Accounts and alerts in Postgres via `pg`, plain SQL migrations, no ORM (team, 2026-10-28)                                                    | The open storage choice of CLAUDE.md §6, made for what must survive a restart; no ORM to learn mid-hackathon                            | Many tables or queries: add a query builder              |
| D29 | Mail via nodemailer over SMTP; without SMTP, development writes to `services/api/.mail-outbox/` (team, 2026-10-28)                           | Any provider works (school SMTP, a Gmail app password, Mailjet); sign-up can be tried locally without one                               | A provider with an HTTP API only                         |
| D30 | Alerts watch places; the percent is fresh count over private per-camera placeholder capacities (team, 2026-10-28)                            | Places are what users see (D20); weighing each camera by its own capacity keeps a silent camera from moving the percent                 | The team measures real capacities                        |
| D31 | Web alerts: inbox + toast over Socket.IO, a browser notification, optional e-mail (team, 2026-10-28)                                         | No new package or service; the e-mail covers a closed tab                                                                               | Phones need alerts: Expo push tokens (still open)        |
| D32 | Replay of readings live YOLO recorded once from licensed footage (`VISION_DETECTOR=replay`) is allowed, labelled demo (team, 2026-10-28)     | One laptop GPU ran 69 of 100 cameras (#39); replay needs no GPU, shows every camera and survives a GPU or footage failure on stage      | Live cameras become cheap enough to run all at once      |
| D33 | Stage preview: on the demo machine, a place's newest frame with YOLO's boxes streams through the API to the place detail on web and phone; off by default (team, 2026-10-28) | Judges see the image processing work, not only its numbers; frames stay in memory, demo footage only, the camera id stays on the server | Any real campus camera, or any run that is not the demo |
